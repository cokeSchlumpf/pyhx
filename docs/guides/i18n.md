# Multilingual apps

`pyhx.i18n` makes an app multilingual: every request has one language, texts are translated with gettext catalogs, and numbers and dates are formatted in that language. pyhx's own texts (components, page templates, login pages) come translated into German, Italian and French; English is the source language.

The sample `samples/user_auth/main.py` shows everything on this page: run it with `poetry run fastapi dev samples/user_auth/main.py`.

## The language of a request

The language is resolved once per request (page or HTMX fragment), from the first of these that names a language the app offers:

1. the language chosen in the session (the language switcher, below),
2. the language of the signed-in user (`RegisteredUser.locale` of commons),
3. the browser languages (`Accept-Language`), by their weight,
4. the app's default.

A regional variant counts as its language (`de-CH` is `de`). The offered languages and the default are settings:

```toml
[app.pyhx.core]
supported_locales = ["en", "de", "it", "fr"]   # default
default_locale = "en"                          # default
```

`negotiate_locale()` returns the language of the current request. Outside a request (a mail, a job, a test) it is the default, unless a block sets one:

```python
from pyhx.i18n import use_locale

with use_locale(user.locale or "en"):
    subject = _("Your report is ready")
```

## Marking texts

Write texts in English and mark them; the English text is the key.

```python
import htpy as y
from pyhx.i18n import _, _l, _n, _p, t

y.h1[_("Cases")]                                         # plain text
y.p[_n("{n} open case", "{n} open cases", count)]        # plural, {n} is filled in
y.button[_p("verb", "Open")]                             # a word with several meanings
y.p[t("Signed in as {name}.", name=y.strong[user.name])] # markup in a placeholder

TITLE = _l("Cases")                                      # defined at import time

@hx.page("/cases", title=_l("Cases"))                    # page titles and nav labels
async def cases() -> y.Node: ...
```

- `_`, `_n`, `_p` translate at once, so call them while rendering, not at import time; for module constants, class attributes, page titles and navigation labels use `_l`, which translates each time the text is shown.
- Placeholders are named and filled after the translation: `_("Case {case} was closed by {user}.", case=c.id, user=u.name)`. A translation can move them (`"{user} hat den Fall {case} geschlossen."`). Never build a sentence from fragments (`_("Closed by") + " " + name`) and never put an f-string into `_()`.
- `t()` returns a list of nodes: the text is escaped, the values (nodes or strings) are kept as they are.
- A comment starting with `# Translators:` right above a call goes into the catalog as a hint for the translator.
- Keep the domain free of texts: use cases return values and codes, the web layer turns them into text.

## Catalogs

An app's catalogs are `.po` files in `locale/` next to its `pyproject.toml`:

```
locale/
  de/LC_MESSAGES/messages.po
  it/LC_MESSAGES/messages.po
  fr/LC_MESSAGES/messages.po
```

(`WebApp(locale_dir=…)` sets another directory.) A text is looked up in the app's catalog of the request language, then in pyhx's catalog, then the English text is used. So an app needs no catalog for pyhx's texts, and it overrides a pyhx text by adding the same text to its own catalog:

```po
# locale/de/LC_MESSAGES/messages.po
msgid "Save"
msgstr "Übernehmen"
```

An app offering a language pyhx doesn't ship (e.g. `es`) translates pyhx's texts in its own catalog. The `.po` files are read when the app starts using a language; there is no compile step and nothing to build.

Two commands keep the catalogs in step with the code (defaults: code in `src/app`, catalogs in `locale/`, the offered languages except English):

```bash
poetry run python -m pyhx.i18n update   # add new texts (untranslated), drop removed ones, keep translations
poetry run python -m pyhx.i18n check    # fail on missing, empty, fuzzy or broken translations
```

Add the check to `poe check`, so a text without translation fails the build:

```toml
[tool.poe.tasks]
i18n-update = { cmd = "python -m pyhx.i18n update", help = "Extract texts into the catalogs" }
check = [
    # … ruff, mypy, pytest …
    { cmd = "python -m pyhx.i18n check" },
]
```

`check` reports a text missing in a catalog or no longer in the code (run `update`), an empty or fuzzy entry, and a translation whose placeholders differ from its source text.

### Translating with an LLM

After `update`, the new entries are empty. An LLM translates them well when it gets the catalog entries with their context: the source references (`#:` lines), translator comments (`#.`), the `msgctxt` of `_p`, and a short glossary of the product's terms. Ask it to keep the placeholders exactly, to fill every plural form, and to leave the `msgid` untouched; then run `check`.

## Switching the language

pyhx provides the behavior of a language switcher, the app its look. Posting a form to `/_pyhx/locale` with the fields `locale` and `next`:

- stores the language in the session (anonymous visitors too),
- stores it on the user as well, for a signed-in registered user (`RegisteredUser.locale`), so it holds on the next sign-in and in other browsers,
- reloads the page (`HX-Refresh` for HTMX requests, else a redirect to `next`), so nothing stays in the old language.

The endpoint comes with the user authentication addon (`configure_user_authentication`, or `configure_user_session` alone). `locale_switch()` returns what a switcher needs (headless): the endpoint, the page to return to, and the offered languages with their own names ("Deutsch", "Français") and which one is current; `None` without a session. Render it in the app's design, e.g. as buttons in the header of `CanvasShell`:

```python
import pyhx.components as c
from pyhx.i18n import locale_switch

def language_switcher() -> y.Node:
    switch = locale_switch()
    if switch is None:
        return None
    return y.form(method="post", action=switch.action, hx_post=switch.action)[
        y.input(type="hidden", name="next", value=switch.next),
        c.button_group(*(
            c.button(o.name, type="submit", name="locale", value=o.locale,
                     variant="outline" if o.current else "ghost", size="sm")
            for o in switch.options
        )),
    ]

hx = WebApp(default_page_template=CanvasShell(header_content=language_switcher))
```

A dropdown or entries of a user menu work the same way: each choice posts `locale` and `next` to `switch.action`.

## Formatting numbers and dates

The `format_*` helpers use the language (and the timezone) of the request; the data tables use the same helpers.

```python
from pyhx.i18n import format_currency, format_date, format_number, format_relative_time

format_number(1234.5)                 # "1.234,5" in German
format_currency(1234.5, "EUR")        # "1.234,50 €"
format_date(case.opened, "long")      # "1. November 2026"
format_relative_time(case.updated)    # "vor 3 Stunden"
```

Also `format_percent`, `format_datetime` and `format_time`. Datetimes are shown in the timezone of the request (see `negotiate_timezone`); naive datetimes are read as UTC.

## Components with labels

`DrawerSelectLabels`, `DrawerRadioLabels` and `ConditionalSelectLabels` show their default texts in the request language; set a field to override it (`DrawerSelectLabels(select_button=_("Apply"))`). Only the fields you set are stored in the component's state, so its other labels follow the language of each request. `CalendarLabels` default to the weekday and month names of the request language.

## Login mails

The email login sends its mail in the language of the person who asked for it: the session language, else the user's stored language, else the browser language, else the default. `SMTPLoginTokenSender` of commons has built-in texts for en, de, it and fr. See [User Authentication](user-authentication.md).
